# F19c2 系统任务手工触发：UX 与契约检查

状态：UX 子智能体已设计，前端实现与独立验收分开记录。依据现有 `POST /tenants/{tenant_id}/scheduled-tasks/{task_id}/runs` 和 [系统任务接口契约](../scheduled-task-api.md)。

## 首期交互

- 在当前租户任务行提供“立即运行”。仅 owner/admin 管理页可见；租户或任务停用时禁用并说明原因。确认框展示租户、任务名、执行目标、计划摘要，说明现在运行一次、不改变下次计划、会产生记录且不能从页面取消。
- 提交时锁定同一任务的再次运行及编辑/启停/删除，播报“正在执行”，不展示虚假进度。同步接口返回后读取 run 的 `status`：`succeeded` 显示成功，`failed` 显示安全错误码，随后打开该任务执行记录；不能只凭 HTTP 201 判断业务成功。
- `TASK_ALREADY_RUNNING` 提示已有计划运行，`TASK_UNAVAILABLE` 提示任务已不可用并刷新定义。403/404 按统一 Problem 安全反馈。网络超时或连接中断时，说明结果无法确认，应先查执行记录再决定是否重试；当前接口重试会产生新运行。
- 窄屏仍可访问动作；对话框可滚动、可用键盘关闭并返回触发位置；开始、成功、失败用文字和 `aria-live` 表达，中英文正式页面均覆盖。

## 服务与归属

服务端从已认证的租户上下文核权，并按 `tenant_id + task_id` 获取定义；前端只缓存当前账号和租户下的任务、运行记录。执行记录只显示安全摘要与错误码，不显示参数、凭据或异常栈。菜单显隐不是授权。

## 契约改进决策（首期之后）

现有同步接口无幂等键，同任务并发调用会串行但各自执行；响应丢失时无法安全重试。可选后续方案：

1. 保留同步接口，接受“先查记录再重试”的人工流程，明确代理超时、无法取消和遗留 `running` 记录的处理方式。
2. 改为先持久化 run、返回 `202 Accepted` 与 run ID，由前端轮询详情；增加按租户、任务、操作者约束的幂等键和遗留运行恢复规则。此方案涉及接口与数据契约迁移，实施前需另写兼容期、旧调用方和回滚方式。

首期采用方案 1，不把页面防连点当作服务端幂等。方案 2 留待产品决定。

## 独立验收条件

真实 API 与浏览器验证：owner/admin 触发成功并定位 run；member/越权不可触发；停用任务和已有 lease 的 409；HTTP 201 + `failed` 正确展示；运行详情脱敏；双击与响应丢失不误导重试；切换租户/撤权后旧响应不污染新页面；窄屏、键盘、读屏提示及中英文文案。代码提交和静态检查不能替代这些验收。
