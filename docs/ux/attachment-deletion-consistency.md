# 附件删除一致性 UX 与接口契约评审

状态：实现前 UX/契约评审；本文是建议合同与验收条件，不代表产品代码已实现或验收通过。

## 评审依据与当前事实

- `docs/tenancy-contract.md` 将附件定义为 Workspace 共享资源、个人附件定义为所有者私有资源；服务端按已验证 tenant/Workspace 上下文及权限授权，租户成员身份不能替代 Workspace 成员权限。
- `docs/attachment-api.md` 规定先删除当前存储及可用保留副本，再删元数据；失败保留元数据，缺失对象可幂等重试。
- `docs/verification/F17c-attachment-s3-storage.md` 的事后 UX review 已指出错误可能落在确认框后面，需在框内明确失败并给重试/取消；键盘、焦点、读屏与窄屏尚无实测证据。
- `apps/api/app/services/attachments.py` 先删主存储，再删 alternate，再条件删除元数据并 `flush()`；storage 错误映射到 `FILE_CLEANUP_FAILED` 或 `ATTACHMENT_STORAGE_UNAVAILABLE`。`get_db()` 在依赖清理时 commit，失败则 rollback。
- `apps/api/tests/verification/test_f17a_attachments.py` 验证了本地清理失败保留元数据，以及 flush 失败后对象已删除、元数据回滚且可重试。测试变量虽名为 `commit_failed`，实际注入 `Session.flush`；这不是 commit 故障证据。F17c 专测尚未覆盖删除故障矩阵。

## 建议结果合同

**完整成功**
- 仅当主对象、配置中的 alternate 保留副本（如有）均确认删除，且附件元数据删除已 commit，才返回 `204` 并展示“已删除”。只完成部分存储清理或只 flush 未 commit 都不能报告成功。
- 对象已不存在视为幂等清理完成；已授权且同时开始的并发删除仍可都返回 `204`。

**主存储/alternate 失败**
- 主存储删除失败：元数据保留，不返回 `204`；维持本地清理错误 `500 FILE_CLEANUP_FAILED`、存储不可用 `503 ATTACHMENT_STORAGE_UNAVAILABLE`。
- 主对象删除成功但 alternate 失败：这是部分清理而非成功；保留元数据供重试，按现有安全码返回失败。提示不可声称所有副本都仍在，也不能指明哪种存储/哪个副本失败。
- 存储调用可能在远端已删除后才超时，因此只要未获完整确认，API/UI 均表述为“删除未确认、可能已部分执行”，不承诺“完全没删”。

**数据库 flush/commit 失败**
- 存储清理成功后 `flush()` 失败：rollback 后元数据应保留，已删对象不会恢复；响应必须失败（通用安全 `500`），重试应依赖对象删除幂等性并最终清理元数据。
- `commit()` 失败绝不可返回 `204`。可确认 rollback 时元数据保留且可重试；提交结果不确定时不推断最终状态，提示结果未确认、刷新列表并允许安全重试。
- 首次 commit 已成功但响应丢失时，重试可能因记录已不存在返回隐私保护的 `404 RESOURCE_NOT_FOUND`。刷新有权查看的列表对账；不得为了幂等而对任意缺失 ID 盲目返回 `204`。
- 当前错误 detail 只有 `code`，客户端可统一显示：“未能确认删除完成；清理可能已部分发生。可以安全重试，或取消后刷新列表。”非 2xx 一律不是成功。是否新增不泄露后端信息的 `delete_outcome: partial|unknown` 是待 API owner 决策；不得自行添加 storage 阶段、后端名或原始异常字段。

**授权、404 与脱敏**
- 未知、跨租户/Workspace、非所有者 personal ID 一律返回相同 `404 RESOURCE_NOT_FOUND`，不泄露附件存在或归属；个人 DELETE 仅所有者可执行，查询须受 owner 和上下文约束。
- Workspace 删除先检查资源作用域，再校验 `resource:delete`；不足返回 `403 FORBIDDEN`。UI 隐藏操作不替代服务端权限检查。
- 404 使用“附件不存在或当前账号无权访问”；任何存储/DB 错误均不得回显 key、Bucket、endpoint、对象路径、凭据或原始 SDK/DB 异常。运维存储设置继续留在服务端，无需新建存储管理 UI。

## 确认框与无障碍要求

- 删除请求中对话框保持打开，确认按钮显示“删除中…”并禁用重复提交；取消/Escape/关闭在请求未决时不可造成额外状态变化。
- 存储/DB 失败显示在确认说明下、按钮上方，留存至重试/取消/新结果；用 `role=alert` 或等效 `aria-live=assertive` 播报“未确认/可能部分执行”。焦点仍在弹窗内，不能只在被遮罩页面显示 toast，也不能只用颜色表达错误。
- 失败后保留目标与文件名，主操作变为“重试删除”，取消可关闭但不表示回滚已发生的清理；关闭后刷新列表。403 提示权限并只提供取消；404 用隐私一致文案并刷新列表，不区分不存在与无权。
- 键盘需验证弹窗焦点进入、Tab 循环、确认/取消可操作、错误播报、关闭后焦点回原删除按钮（行消失则回列表标题/相邻操作）。窄屏需保证长文件名/错误可换行、按钮无裁切、弹窗可滚动；验收 320 CSS px 和 200% 缩放。
- 刷新发现附件已不在当前可见列表时移除陈旧行，但不把隐私 404 宣称为 DELETE 已确认成功。成功提示只在 `204` 后显示。

## 可测试验收标准

1. 主存储删除异常：非 `204`、映射为现有安全错误码、元数据保留；响应不含注入的 endpoint/Bucket/key/凭据/异常信息。
2. 主存储已删、alternate 删除失败：失败而非成功、元数据保留、主对象可不存在且 alternate 保留；修复故障后同一授权重试以缺失对象幂等清理，完成剩余清理及 commit 后为 `204`。
3. storage 清理后注入 `flush()` 失败：非 `204`、事务 rollback、元数据保留、对象已删除；撤销故障后重试 `204` 且元数据消失。测试必须称为 flush 故障。
4. 单独注入真正的 commit 阶段故障：绝不误报 `204`；确定 rollback 时验证可重试，不确定时不假设 DB 状态，验证刷新/安全重试能对账并且不泄露 DB 异常。
5. 保持并发删除与对象缺失但元数据仍存时重试通过；未知/跨作用域/非本人 personal ID 同为 404；Workspace 缺 `resource:delete` 为 403 且不访问存储。
6. UI 仅在 204 报成功；存储/DB 错误位于确认框内，清楚提示未确认/可能部分执行，重试与取消可用、重复提交禁用；404 刷新列表且不泄露归属，行不可见时清除陈旧项。
7. 键盘/读屏验收焦点约束、错误播报与返回焦点；窄屏/放大验收无溢出/裁切。API 与 UI 检查存储错误完全脱敏；模拟 S3 客户端测试仍不等于真实 RustFS CRUD。

## 假设与待决事项

- 假设：`alternate_store_for()` 是迁移/回退期间需清除的旧副本；删除覆盖主对象及该副本，不存在另行规定的永久保留/回收站语义。
- 待 API owner 决策：是否新增机器可读 `delete_outcome` 区分已知部分清理与结果未知。决策前客户端统一用“未确认、可能部分执行”，不推断精确状态。
- 待产品决策：commit 不确定后重试得到 404，只提示“列表已更新”，还是可基于当前授权列表缺项提示“当前列表中已移除”。决策前不得盲目返回 204 或宣称 DELETE 成功。
- `ApiProblem` 未保留 `request_id`、列表加载重试和迁移 CLI 安全失败分类是 F17c 记录的相邻事项，不阻塞本合同；若展示 request ID，只能使用服务端已正式提供的安全 ID。
