# Synapse 集成计划

状态：实施中。前端框架与后端基础已建立；各功能实际完成及独立验证状态见 development-status.md，本计划中的功能清单不代表已经完成。

## 目标与架构

- 前端：以现有 shadcn-admin 为基础，使用 Vite、React、TypeScript、TanStack Router、TanStack Query、Tailwind CSS、shadcn/ui。
- 业务后端：保留 Synapt 的 FastAPI、SQLAlchemy、Pydantic、Alembic 及指定业务模块。
- AgentScope：将 Demo 前端移植至同一个 React 应用；通过 AgentScope 应用工厂嵌入同一个 FastAPI 服务进程，使用一个后端启动入口。
- 用户只使用一套 Synapse 账号、导航与权限体系。
- 新增租户管理、协作 Workspace 管理，以及前端左上角 Workspace 切换器；先完成租户和空间隔离，再迁移各业务模块。
- 项目名称为 Synapse；旧 Synapt 项目是迁移来源。

## 租户与 Workspace（新增基础能力）

### 概念和层级

租户代表一个公司、组织或客户，是业务隔离边界。每个租户拥有多个协作 Workspace，例如研发空间、客服空间。账号是全局登录身份，通过成员关系加入租户及其 Workspace；同一账号可以加入多个租户和空间。加入租户不自动获得所有 Workspace 的业务数据访问权限。

```text
Synapse 平台
├── 租户 A：公司 A
│   ├── Workspace：研发
│   └── Workspace：客服
└── 租户 B：公司 B
    └── Workspace：业务团队
```

Synapse 的协作 Workspace 管理成员、业务资源与权限；AgentScope 的 runtime workspace 管理智能体的执行目录、文件和记忆。两者通过明确映射关联：一个协作空间可以有多个智能体运行目录，命名分别采用 workspace_id 与 runtime_workspace_id，避免混用。

### 功能清单

| 模块 | 功能 |
| --- | --- |
| 租户管理 | 创建、编辑、启停、归档、租户管理员分配和基础设置 |
| 租户成员 | 添加/邀请、移除、成员状态、租户角色；邀请先提供链接机制，邮件发送另配服务 |
| Workspace 管理 | 创建、编辑名称与图标、查看、归档、成员管理和空间设置 |
| Workspace 成员 | 添加租户成员、分配角色、移除成员、移交所有权；避免移除最后一位所有者 |
| 权限 | 平台管理员、租户所有者/管理员/成员、空间所有者/管理员/成员/只读角色，按作用域授权 |
| 左上角切换器 | 当前租户与空间名称、按租户分组的空间列表、搜索、切换、空间设置、有权限时创建空间 |
| 当前空间状态 | 记录最近访问空间；无空间/已归档/权限撤销时提供选择或创建入口 |

新增的 SaaS 租户管理属于平台基础管理，与已排除的 Synapt 原“平台管理”业务模块分开。平台管理员默认管理租户生命周期，其身份不自动赋予读取全部聊天、凭据、人脸数据的权限。

### 数据与权限范围

| 作用域 | 数据 |
| --- | --- |
| 全局 | 账号登录身份、平台租户记录、系统可用菜单/权限定义 |
| 租户 | 租户成员、部门、租户角色、租户配置及字典覆盖 |
| Workspace | 智能体、知识库、附件、人脸库、任务、渠道、空间资源库及空间设置 |
| 空间内个人 | 默认私有的聊天会话、个人凭据与个人资源；资源类型允许时再显式共享 |

账号资料和密码由账号本人或明确授权的账号管理接口维护；租户管理员通过租户成员关系管理成员，不能以租户管理权限修改其在其他租户的身份或权限。

新增 tenants、tenant_members、workspaces、workspace_members 等实体，以及按作用域关联的角色权限模型。Workspace 业务记录保存租户和空间归属，使用外键、组合约束及统一查询上下文防止跨租户关联。原角色/用户模型不能仅靠新增菜单完成多租户化。

首期使用共享数据库、按租户/空间字段隔离；Redis 命名空间、向量存储、文件路径和后台任务同样带有范围信息。数据库独立部署等更强隔离方式留作后续扩展。

### Workspace 切换流程

1. 用户登录，后端返回可访问租户和空间；恢复最近空间前重新校验成员资格。
2. 左上角选择空间后进入 `/w/<workspaceId>/...`，租户由服务器根据空间归属确定。租户管理和个人账号页面使用单独路由。
3. 每次空间请求携带空间上下文，后端验证账号、租户、空间状态、成员资格及操作权限；浏览器保存的空间 ID 只是请求信息。
4. 空间变化后重新加载菜单、权限、列表和资源；TanStack Query 缓存键包含账号、租户、空间和资源参数，所有请求捕获发起时的上下文，避免异步响应写入新空间。
5. 有未保存表单时提醒用户；停止旧空间的前端订阅，旧空间正在运行的 AI 任务保留原归属。切换本身不自动取消后台任务，返回后可继续查看。
6. 详情页切换到其他空间时回到对应列表或空间首页，不沿用旧空间资源 ID。退出登录、移除成员、空间停用或权限变化时使相关缓存和访问状态失效。

### AgentScope 与其他模块适配

- 统一身份适配传递经过校验的 tenant_id、workspace_id、actor_user_id；不能仅将 workspace_id 当成所有人的共同用户 ID。
- 对 AgentScope 的个人资源建立包含租户/空间/用户的稳定归属映射，对共享资源使用明确的授权策略；保留操作者身份，防止空间成员读到彼此私有凭据和会话。
- AgentScope 的资源访问策略、存储适配、运行目录及索引均需覆盖空间范围；只改前端过滤或 get_current_user_id 不足以完成空间隔离。
- 工作目录、文件下载与预览签名、知识库检索、SSE、后台索引、AI 定时任务、渠道账号绑定均继承创建时的空间，并执行对应权限规则。
- 人脸库和识别搜索按空间限定；未登录的人脸登录只使用明确绑定的租户/登录上下文及登录策略，不跨租户全库检索。
- 系统任务携带租户和空间上下文，执行时校验其有效授权；旧数据迁移时显式指定目标租户、默认空间和资源归属。

这些能力列为登录完成后的基础阶段，在批量业务迁移前实现。验收至少覆盖两个租户、每个租户两个空间、一个跨空间账号，以及成员移除、越权资源 ID、缓存切换、异步响应和后台任务归属场景。

## 排除范围

- Synapt 平台管理中除人脸识别外的业务：告警、平台应用接入、流媒体、人员资质、旧 LLM/MCP 管理页面。
- Synapt 加密管理全部业务：代理、浏览器环境、项目管理、虚拟身份/账号/钱包、币安相关功能。
- 旧资质识别体验及独立语音体验链路不自动搬入；AI 前端范围以 AgentScope Demo 为准。
- 排除需覆盖路由、导航、服务、模型注册、初始化数据、后台任务和专属依赖。共享认证、文件等基础能力按保留功能需要提取。
- “移除加密管理”是移除该业务模块，密码哈希、登录加密、凭据保护等基础功能仍需使用。
- AI 模型与凭据入口由 AgentScope 能力提供，不迁入旧平台的重复页面。

## 同一个 FastAPI 服务的集成方式

1. Synapse 主应用提供 `/api/v1/system/*` 和 `/api/v1/face/*`；前端同步调整接口地址。
2. 使用 AgentScope `create_app()` 创建内部子应用，挂载在 `/api/v1/ai`；与主应用共享同一服务进程和监听端口。
3. 显式组合主应用与 AgentScope 的 lifespan，统一启动/关闭存储、消息总线、调度器、索引及渠道任务。单纯挂载不会自动运行子应用 lifespan。
4. 在 AI 子应用覆盖身份依赖，使用 Synapse 已验证的用户、租户和 Workspace 上下文；同时覆盖无身份依赖的管理端点，制定授权规则。
5. 统一账号的基础上落实租户/空间归属、个人私有范围与角色权限。普通用户不能通过传入其他空间的资源 ID 或 X-User-ID 访问会话、文件和凭据；渠道入口采用相应的可信身份与空间绑定。
6. 浏览器统一访问相对路径，不再填写独立服务 URL 或任意用户名。适配原 Demo 中以 `/` 开头的 URL 拼接，覆盖上传、下载、预览、签名链接和 SSE 地址。
7. 前端接入共同的主题和组件，React Router 页面改写为 TanStack Router；保留 AgentScope 已有数据类型及流事件协议，普通接口由请求适配层处理。
8. TanStack Query 管理列表和接口缓存；聊天流由独立流式处理逻辑消费，完成后同步会话缓存。
9. 系统任务和 AI 定时任务使用不同模块与任务标识；初期采用单个后端 worker，防止重复调度。多 worker 配置另做验证。

直接融合需要在同一个 Python 环境解决依赖兼容。以 Python 3.11+ 为起点，统一 FastAPI、Starlette、Pydantic 等约束，精简旧项目无关依赖，锁定经过启动和联调验证的版本。AgentScope 按明确版本或 commit 引入，并保留来源及许可证。

## 存储策略

- 系统与人脸业务先沿用现有 SQLAlchemy 模型和开发数据库方案，建立 Synapse 自己的数据初始化及迁移流程。
- AgentScope 初期沿用 Demo 的 Redis 存储方案并启用持久化；工作空间使用专属持久化目录。
- 知识库向量和上传文件必须持久化，不能直接沿用 Demo 的内存 Qdrant 配置作为正式存储。
- 一个后端入口仍可使用 SQL 数据库、Redis、向量存储和文件存储；合并服务不要求重写为单一数据库。
- 迁移代码不默认复制旧库全部业务数据或密钥；初始化只包含保留模块的菜单、权限和必要字典。
